## 开始前

确认输入文件：

- 文件存在且可打开。
- 文件格式为 `.docx` 或 `.pdf`。
- 若用户提供评分细则或学校模板，优先级高于默认国赛标准。
- 若用户提供优秀论文样例，先按 `exemplar-library.md` 整理入库；审稿时只读取被标签匹配选中的候选样例和核心样例。
- 正式审稿必须按 `exemplar-library.md` 的外部权威参考规则联网检索相关数模论文、学术论文、教材级资料、官方文档或高质量综述；本地样例是否匹配不影响这一步。

## 用户引导和进度提示

第一次进入审稿任务时，先把流程说清楚，但不要写成长说明。推荐格式：

```text
我会先建立本次 case 目录保存原件，再按国赛标准、题目要求、图表证据链和权威资料生成同格式标注文件。
```

随后检查材料：

1. 待审论文：必须有 `.docx` 或 `.pdf`。
2. 题目文件：用于判断问题覆盖、模型适配和结果是否回答题意。
3. 评分标准、`format` 或学校模板：用于覆盖默认国赛标准。
4. 优秀论文样例：可选增强，用于学习同题型写法、图表组织和结构节奏。

若材料已足够启动，直接开始处理。若材料不全，不要一次性列出很长的说明，只问最关键的缺口，或说明降级后的审阅范围。

细活阶段要用一句话让用户知道当前在做什么。提示应短、具体、事实性，适合放在工具调用前或阶段切换时：

- 建 case 前：“我先把材料复制到本次 case 目录，避免改动原文件。”
- 抽取前：“我正在抽取正文和版式信息，用来定位后续批注。”
- 图审前：“我正在生成图表清单，先防止漏审图片、表格和关键结果图。”
- 标签前：“我正在给论文打标签，用于匹配样例和生成检索词。”
- 样例匹配前：“我正在匹配本地样例；匹配不足时会继续依赖权威外部资料。”
- 外部检索前：“我正在检索权威资料，并记录来源、用途和检索日期。”
- 写回前：“我正在把审稿意见写回同格式副本，不覆盖原文。”
- 验证前：“我正在渲染检查输出文件，确认标注可见且不遮挡正文。”

提示频率以阶段为单位；不要为每条批注、每页图片或每个临时文件重复提示。

## 材料缺失与降级

材料不足时按下面规则继续：

| 缺失材料 | 可以继续做什么 | 必须提醒用户什么 |
|---|---|---|
| 待审论文 | 不能开始正式审稿 | 需要提供 `.docx` 或 `.pdf` |
| 题目文件 | 可审格式、语言、结构、图表表达、可复现性 | 题意覆盖和结果是否答题只能初判 |
| 评分标准/format | 可按默认国赛标准审阅 | 用户补充当年评分细则后可再复核 |
| 优秀论文样例 | 可按默认标准、题目和权威资料审阅 | 本地优秀论文对标能力降低 |
| 外部检索工具 | 可生成检索词和待查资料清单 | 正式审稿需要权威资料；用户需开启联网能力、配置工具或提供链接 |
| 原始数据/代码 | 可指出图表和结论的可疑点 | 数据合理性不能替用户确认，只能标为“需确认” |


没有优秀论文时，不要停止审稿，也不要降低为泛泛润色。继续执行：

1. 读取默认国赛标准和当次题目/评分标准。
2. 为论文打标签，生成方法、题型、数据和图表标签。
3. 跳过或空跑本地样例匹配，在报告中写明“无可用本地样例”。
4. 必须联网检索权威资料；若暂时不能联网，生成检索词和待查资料清单。
5. 审稿意见中区分“可以确定的问题”和“需要用户提供数据/代码后确认的问题”。

对新用户，优先给可执行下一步，而不是让用户理解所有内部文件。示例：

```text
现在可以先审稿；没有优秀论文只会影响样例对标，我会用默认国赛标准、题目要求和权威外部资料补足。
```

## 试审与审稿文件夹

当用户提供待审题目和论文时，先在当前项目根目录创建或复用 `math-modeling-review-cases/<case-id>/`，不要把待审文件混入样例库。

推荐结构：

```text
math-modeling-review-cases/
└── <case-id>/
    ├── problem/
    ├── paper-original/
    ├── reviewed/
    └── work/
```

处理规则：

1. `<case-id>` 用题目年份、题号或短标题生成；信息不足时用 `trial-YYYYMMDD-HHMM`。
2. 将用户提供的试题或评分细则复制到 `problem/`。
3. 将用户提供的待审论文原件复制到 `paper-original/`。
4. 所有渲染图、OCR 中间结果、标签草稿和临时分析放入 `work/`。
5. 审阅后的同格式文件只放入 `reviewed/`，命名为 `原文件名_reviewed.ext`。
6. 不覆盖 `problem/` 和 `paper-original/` 内的原件；若用户再次提供修订版，追加版本后缀。
7. 交付时给出 `reviewed/` 中的最终文件路径，并说明本次 case 目录。

## 可复用脚本

稳定、重复出现的执行步骤应优先使用 `scripts/review_case_tool.py`，不要继续为每个案例重写 `extract_case.py`、`render_and_inventory.py`、`make_reviewed_pdf.py`、`verify_reviewed_pdf.py` 这类一次性脚本。

推荐边界：

1. `scripts/`：放通用执行脚本和模板说明。
2. `references/scripts/`：只放维护参考资料的脚本，例如同步样例索引。
3. `math-modeling-review-cases/<case-id>/work/`：只放本案例的中间文本、渲染图、图表清单、`issues.json`、定位结果和验证报告。
4. `math-modeling-review-cases/<case-id>/reviewed/`：只放最终同格式审阅文件和通用文本提示清单。

常用步骤：

1. `init-case`：创建 case 目录并复制题目、评分标准和论文原件。
2. `extract`：抽取 `.docx`、`.pdf` 和旧 `.doc` 的可读文本或粗提取文本。
3. `render-pdf`：渲染 PDF 页面并生成图表清单和接触图。
4. `inspect-docx-media`：导出 DOCX 嵌入图片并生成图片接触图。
5. `build-figure-inventory`：生成 `figure_inventory.json` 和 `figure_inventory.md`，防止漏审图题、表题、内嵌图片和关键结果表。
6. `build-figure-patterns`：从优秀论文抽取图表标题，生成本地图表类型模式库。
7. `match-exemplars`：根据待审论文标签匹配本地优秀论文样例，生成候选样例、核心样例和选择理由。
8. `search-references`：根据待审论文标签和方法关键词检索权威外部资料，生成 `external_references.json`、`external_reference_report.md` 和外部参考卡片草稿。
9. `make-feedback-template` / `build-feedback`：把权威点评视频、文档、网页或教师评语整理成长期样例匹配反馈记录。
10. `make-figure-review-template`：生成结构化图审证据链草稿。
11. `build-figure-issues`：把图审证据链转成 `figure_review.json` 和 `figure_issues.json`。
12. `make-issues-template`：生成 DOCX/PDF 对应的审稿意见草稿模板。
13. 审稿判断完成后，先把批注整理为 `work/*_issues_draft.md`，再用 `build-issues` 生成并校验 `work/issues.json`。
14. `build-reference-report`：汇总本地样例、外部资料、资料支撑的建议类型和仍需用户确认的数据项，生成 `work/reference_report.md`。
15. `write-docx-review`：生成黄色原文高亮 + 蓝色可见提示段的 DOCX。
16. `write-pdf-review`：生成描边框 + 编号 + 末尾提示页的 WPS 兼容 PDF。
17. `verify-pdf`：检查 PDF 页数、定位缺失数，渲染关键页，并生成 `render_acceptance.json` 验收彩色标注和提示页可见性。
18. `run-regression-tests`：修改脚本后运行，保护 A229/B203/C008 抽象出的 PDF 标注、DOCX 高亮、图审 JSON、图表清单和参考来源报告能力。

脚本只负责执行，不负责替代审稿判断。若 `issues.json` 中缺少定位、页码、需确认项或图表证据，应先补齐审稿判断再写回。

维护脚本时读取 `regression-tests.md`，并在提交前运行 `run-regression-tests`。测试 fixture 不包含私有论文原文，输出放在已忽略的 `math-modeling-review-cases/_regression/`。

## 总文件夹解析

当输入是一个总文件夹时，按以下结构解析：

```text
总文件夹/
├── 题目/
│   └── 2024/
│       ├── A/
│       │   ├── 题目.docx
│       │   └── 题目.pdf
│       ├── B/
│       ├── C/
│       ├── D/
│       └── format/
└── 优秀论文/
    └── 2024/
        ├── paper-a.pdf
        └── paper-b/
            ├── 1.jpg
            ├── 2.jpg
            └── ...
```

处理顺序：

1. 先定位 `题目/年份/format`，评分标准必读。
2. 在每个 `A/B/C/D` 子文件夹中，优先选择一个可读文件：`.docx` 优先，其次 `.pdf`。
3. 如果同时存在多个可读题目文件，只读取一个即可，避免重复。
4. 再进入 `优秀论文/年份`，按 PDF 和图片论文分别入库。
5. 图片论文文件夹中的 `jpg` 按顺序视为论文页码顺序，必要时结合 OCR 或视觉方式处理。
6. 完成入库后，再进行标签化、样例匹配和审稿。

## 文档读取

### `.docx`

1. 读取正文结构、标题层级、段落、表格、公式附近文本、图片和图题。
2. 提取或渲染图片，记录图片所在章节和上下文。
3. 保留原文样式，准备输出副本。

### `.pdf`

1. 提取文本和页面布局。
2. 渲染页面，用于检查版式、图表和图片内容。
3. 记录页码、段落位置、图片位置和正文引用。
4. 如果文本不可提取，使用页面图像进行视觉审阅，并在最终说明中注明定位精度限制。
5. 如果发现疑似扫描件，先进入扫描件分流，不要默认当作可提取正文处理。
6. 若 Poppler 命令不可用或包装命令失效，可改用 `pypdfium2` 渲染页面；渲染能力本身比具体命令更重要。
7. 对可提取文本的 PDF，也必须渲染关键页和图表页；文本提取只能证明“能读字”，不能证明图表、公式和标注可见。

### 旧 `.doc` 评分标准

- `.doc` 旧格式可能只能粗略抽取文本，容易出现乱码或结构缺失。
- 若评分标准无法可靠读取，应在最终说明中写明，并以题目、默认国赛标准和可读材料为主进行审阅。
- 不要把旧 `.doc` 的粗提取结果当作完整评分细则引用。

## 扫描件分流

当 PDF 文本提取为空、正文明显是图片层，或页面视觉上呈现扫描件特征时：

1. 先判断是否有水印。
2. 有水印 -> 要求用户先去除水印并重新提供文件。
3. 去除后 -> 再询问是否按图像版论文处理。
4. 若用户确认按图像版处理 -> 渲染页面、按页阅读、建卡、打标签、提取摘要级总结和关键词。
5. 若用户不接受图像版处理 -> 要求提供可直接读取的版本，或者放弃该论文。
6. 无水印 -> 直接询问是否按图像版处理。
7. 只有用户确认按图像版处理后，才继续后续流程。

## 扫描论文 OCR 入库

当用户明确提供去水印后的扫描论文并授权直接处理时，按 `scanned-paper-ocr.md` 执行：

1. 渲染首页或必要页为图片。
2. 使用 OCR 提取首页标题、摘要、关键词和主要方法。
3. 根据 OCR 文本判定是否可读。
4. 可读则生成 OCR 侧写、样例卡片和索引标签。
5. 替换原不可读源文件前先备份。
6. 若目标文件被 PDF/WPS 等进程占用，不强制覆盖，放入待替换目录并在报告中说明。
7. 不可读文件不替换，列入报告等待用户决定。
8. 入库完成后执行整理后复核：刷新索引和 manifest，检查文本状态、待复核项、OCR 报告、样例卡片和标题/标签误判。

### 题目与评分标准

- `format` 必须优先读取并作为当年评分标准。
- 同一题若存在 `.docx` 和 `.pdf`，先读更易提取文本的那个，另一个仅在需要核验版式时再读。
- 题目文件只需用于理解题意、子问题和评分约束，不作为样例库内容。

## 待审论文打标签

审稿前先为待审论文生成标签，不需要长篇分析。至少覆盖：

- 题型标签：优化、预测、评价、分类、仿真、机理建模、统计分析、图论网络、时间序列、空间分析等。
- 方法标签：线性/非线性规划、整数规划、层次分析、熵权法、TOPSIS、回归、机器学习、聚类、微分方程、蒙特卡洛、元胞自动机等。
- 数据标签：表格数据、时间序列、空间地理、图像、文本、多源数据、缺失数据、小样本等。
- 论文结构标签：摘要强/弱、图表密集、公式密集、代码依赖、结果导向、理论推导导向等。
- 问题标签：摘要缺结果、模型解释不足、图表弱、检验不足、格式问题、语言问题、符号不一致等。

标签用于匹配样例和决定审阅重点，不直接替代审稿判断。

## 样例匹配

如果 `references/exemplars/index.md` 存在：

1. 先运行 `match-exemplars` 或读取索引，不读取所有样例全文。
2. 根据待审论文标签筛选 5-8 篇候选样例，再选 3-5 篇核心样例或卡片精读；如果样例总数不足，使用全部可用候选并说明局限。
3. 优先匹配题型和方法，其次匹配数据类型、图表组织和结构特征。
4. 根据索引中的“卡片”列，只读取被选中样例的 `_catalog/cards/<year>/<sample-id>.md` 或必要片段。
5. 在最终交付说明中简短写明候选样例、核心样例和选择理由，不暴露过多样例内容。
6. 必须说明本次实际读取的是“样例卡片”“样例片段”还是“样例全文”；不能把只读卡片说成读了全文。
7. 必须执行外部权威资料检索，说明来源、检索日期、可信度和每条资料用于支撑哪类判断。
8. 优先用 `search-references` 生成检索记录；脚本输出的可信度只是来源初筛，不能替代审稿判断。
9. 完成样例匹配、外部检索和结构化批注后，运行 `build-reference-report` 生成 `work/reference_report.md`；交付时必须给出该报告路径。

`match-exemplars` 的分数只用于排序和解释，不是论文质量分。若存在 `math-modeling-review-cases/_learning/exemplar_feedback_log.jsonl`，脚本会读取权威点评反馈作为轻量校准提示；单条反馈不能直接改写固定权重，核心判断仍要回到题目、论文和图表证据链。

如果没有匹配样例：

- 说明本地样例库没有可用对标样例或匹配度不足。
- 仍必须检索相关数模论文、学术论文或权威方法资料，整理外部参考卡片后再审稿。
- 不要因为没有本地样例就退化为普通 GPT 式泛泛审阅。

## 优秀论文入库

对 `优秀论文/年份` 下的内容：

- 论文 PDF：按单篇样例处理，生成样例卡片。
- 图片文件夹：按页序读取，必要时识别为图像版论文，生成样例卡片。
- 先给样例打标签，再决定是否纳入本地样例索引或外部索引。
- 若样例质量高，优先加入本地样例索引；若来源是网络检索，再放入外部参考索引。
- 完成入库后必须复核索引、manifest 和本轮样例卡片；确认无 `待人工复核`、空标签、空关键词或明显 OCR 误判后，才视为整理完成。

## 内容审阅

按顺序检查：

1. 摘要：是否有方法、结果、结论和关键词。
2. 章节结构：是否覆盖题目全部问题。
3. 问题分析：是否形成建模路线。
4. 假设与符号：是否合理、一致、必要。
5. 模型建立：目标、变量、约束、公式、解释是否完整。
6. 模型求解：算法、参数、过程、结果是否可复现。
7. 结果分析：是否回答问题，有无检验和解释。
8. 模型评价：优点、缺点、改进、推广是否具体。
9. 参考文献和附录：引用、格式、代码放置是否合适。
10. 全文语言：措辞、语病、标点、编号、单位、符号一致性。

用户确认的增强审查追加：

11. 正文页数是否达到 25 页且不超过 30 页，统计口径需明确，且不得以重复内容凑页数。
12. 摘要正文是否不少于 700 字；不设置固定上限，并检查各小问方法、量化结果、结论和创新点是否覆盖。
13. 误差、灵敏度、稳健性三类检验是否齐全；不适用时是否有合理解释和替代验证。
14. 图片是否足以支撑问题分析、模型结构、关键结果和检验；公式、表格、参考文献和对比实验按题目合理性判断，不设机械数量门槛。
15. AI 痕迹风险是否有可观察证据；仅凭文风不得直接定性违规，不检查 AI 工具使用详情或 AI 声明一致性。
16. 流程图只审逻辑、可读性、尺寸、箭头和正文一致性，不要求 Graphviz。


## 数据建模常见风险点

对消费、会员画像、用户画像、评价分类、聚类、回归、关联规则等数据驱动论文，重点检查：

1. 数据粒度：一条记录是否等于一次消费、一张小票、一个商品明细或一次用户行为，必须由字段和业务含义支撑。
2. 阈值来源：金额区间、次数区间、活跃/沉默/流失阈值、评分分档不能只凭主观设定；优先要求分位数、业务规则、聚类结果或敏感性分析。
3. 指标相关性：RFM/RFMT、评价指标体系、因子分析变量等应检查冗余和相关性，避免多个高度相关指标重复计分。
4. 权重方法：层次分析法要检查判断矩阵、CI/CR 解释和一致性阈值；不要把 CI 越小越混乱这类概念写反。
5. 聚类结果：检查 K 值选择、初始化、迭代次数、SSE/轮廓系数、类别人数和业务解释；若某些类只有极少样本，需说明是否异常类。
6. 概率与得分：因子综合得分、评价得分、聚类距离不天然等于概率；若称为“激活率”“转化率”等概率，需有映射、标签或历史验证。
7. 回归结论：不能只凭系数正负下结论，应报告 R2、p 值、残差检验、变量显著性、多重共线性和样本口径。
8. 关联规则：必须报告支持度、置信度、提升度、最小阈值和购物篮构造方法；只列商品组合不足以支撑促销方案。
9. 附录复现：代码、软件、参数、输出文件和正文表图应有对应关系；附录不能只堆代码。

## 图表审阅

对每张图片和关键表格建立审阅记录：

- 页码或章节。
- 图表类型。
- 图题或表题。
- 正文引用句。
- 图表本体内容。
- 前后文声称的结论。
- 图表承担的功能。
- 证据判断：支持、部分支持、不支持或无法判断。
- 数据来源、计算口径、脚本或原始记录是否可追溯。
- 需确认项。
- 主要问题。
- 具体改进建议。

结构化图审记录按 `figure-review.md` 执行。先生成 `figure_review.json` 保留证据链，再由 `figure_issues.json` 写回批注；不要只在普通 `issues.json` 中写一句笼统的“优化图片”。

执行规则：

1. 先运行 `build-figure-inventory` 建立图表清单，再逐项看图表本体、图题/表题和正文解释，不能只按作者文字判断。
2. 对数据图、结果图和结果表，核对变量、单位、坐标、统计口径、样本范围、有效数字和正文结论。
3. 当数据合理性无法从论文、题目、附件、代码或中间结果中验证时，不给“正确/合理”的结论；在批注中写“需确认”，要求作者提供图表数据取得方法、原始数据记录、计算脚本或模型输出。
4. 对流程图、算法图和模型结构图，通读前后文，核对节点顺序、箭头方向、输入输出、分支条件、循环条件和终止条件是否与正文一致。
5. 对已有成熟模型、经典算法或标准流程，必要时检索权威论文、教材、官方文档或高质量综述进行对照；记录使用的来源和检索日期。
6. 每条图表批注都应包含内容判断和美化建议；美化建议至少覆盖清晰度、字号、线宽、配色、图例、坐标轴、单位、图题或版面位置中的相关项。

如果发现应新增图片，优先建议这些位置：

- 问题分析末尾：建模总流程图。
- 数据预处理后：数据分布、异常值处理、缺失值处理前后对比。
- 模型建立后：模型结构图或算法流程图。
- 结果表格后：核心结果可视化。
- 模型检验处：误差、残差、敏感性或对比图。

## 标注写回

1. 复制原文件为新文件。
2. 在副本中添加高亮和批注。
3. 批注靠近问题位置，但不遮挡正文。
4. 对大段问题只标关键句，批注中说明影响范围。
5. 对缺失内容，在建议插入位置附近添加批注。
6. 对图表建议，标在图表、图题/表题或正文引用句附近；如果是数据合理性问题，优先标在正文引用句或结论句附近，并写明需要作者提供的数据来源或脚本。
7. 对样例启发出的改进，批注中说明“可参考同类优秀论文写法”，但不要要求照搬样例。
8. 对 PDF 输出，同时生成通用文本提示清单，格式为“页码、原文定位、问题类型、修改提示”。不要只依赖 PDF 批注对象；若用户使用 WPS 或批注不可见，将提示清单作为主要交付，并可把提示页直接追加到 PDF 末尾。
9. 若用户要求“原文定位要在文中高亮标出”，或批注在 WPS 中不可见，则生成 WPS 兼容 PDF：把定位框、下划线和编号直接合并进页面内容，避免用不透明色块覆盖正文；编号与提示清单或追加提示页对应。
10. PDF 合并标注时要警惕透明填充失效：某些 `merge_page`/阅读器组合会把透明色块变成不透明色块，遮挡正文。优先使用描边框、下划线、编号圆点；除非渲染验证通过，否则不要使用大面积填充。
11. 自动文本定位失败时，不要交付漏标结果。应使用全文搜索、页码核对、图表清单和必要的手工页区坐标补齐，直到每条提示都有对应定位或明确说明无法定位。

## 视觉验证

交付前尽可能渲染输出文件，检查：

- 批注是否可见。
- 高亮是否定位准确。
- 批注是否遮挡正文、图表或页码。
- 图片和表格未因写回操作变形。
- 页码、章节和编号未被破坏。
- 图表批注是否靠近图表本体、图题/表题或正文引用句，且不遮挡图表关键信息。
- PDF 输出页数是否符合预期：原文页数 + 追加提示页页数。
- 定位命中数是否等于提示总数；若有 missing，先修复或在交付中说明。
- 若修改过标注样式，重新渲染关键页，不沿用旧的接触图判断。
- 对 PDF，优先以 `verify-pdf` 生成的 `render_acceptance.json` 为底线验收；若彩色标注像素不足、提示页为空或关键页接触图异常，先修复再交付。

如验证失败，修正后再次渲染。

## 交付

交付内容：

- 标注后的同格式文件路径。
- 通用文本提示清单路径；若生成了带提示页的 PDF，也一并给出。
- 参考来源报告 `work/reference_report.md`，说明本地样例、外部资料、支撑建议和需用户确认的数据项。
- 本次 case 目录路径，确认题目原件、论文原件和审阅输出已分开保存。
- 简短列出最关键的修改方向。
- 待审论文标签、候选样例/核心样例编号、外部权威资料来源和选择理由。
- 说明是否存在无法自动写回或无法可靠识别的部分。

交付时对新用户优先说明“在哪里看结果”和“哪些还需要补材料”，可使用这种短格式：

```text
审阅后的文件在 reviewed/；参考来源报告在 work/reference_report.md。仍需确认的主要是图表数据来源和生成脚本，具体项已写入报告。
```

不要把完整批注内容再次长篇复述给用户，除非用户要求。
